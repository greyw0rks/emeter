# Threat model

This is an experimental payment engine using one immutable zero-value DEMO token. Its security checks establish bounded authorization, isolated accounting, and circuit enforcement; they do not constitute an audit or production payment readiness. The original isolated proof and the newer session vault are separate deployments.

| Threat | Current control | Remaining boundary |
| --- | --- | --- |
| Forged customer grant or charge | EIP-712 binds chain ID and vault. Customer grants bind key, budget, limits, expiry, settlement window, service set, and nonce; delegated charges bind request ID/hash, service, price version, maximum, nonce, and validity. EIP-1271 customer/session signatures are supported. | The browser and gateway must present and verify the same terms. Mainnet proof customers are builder-controlled EOAs. |
| Session key increases its authority | Only the customer can sign the session grant or the exact charge-bound soft-limit override. Hard budget and per-request cap cannot be overridden. | Compromised keys can spend within their signed scope until revoked. Emergency revocation also blocks outstanding charges. |
| Forged provider response | Exact TAP-13 digest and low-s signature verification against the signer in the immutable selected price version. Version revocation blocks a compromised signer. | Full TAP-11 resolution and untrusted HTTP envelope verification remain gateway work. |
| Price or payout changes after authorization | Charges pin immutable price versions, including signer, payout, container identity, and price. | A provider or registry owner can revoke a version, service, or provider and prevent pending settlements. |
| Provider reports a useless or incorrect result | Request and body are attributed to the provider. | Signature does not prove quality. Success reporting, delivery acknowledgement, and customer acceptance must remain separate. |
| Receipt moved to another request | Customer authorization and provider signature both bind ID and request hash. | Canonical JSON/transport parsing for untrusted HTTP requests is separate gateway work. |
| Duplicate settlement | Session-scoped request IDs and nonces, and globally consumed receipt digests, are recorded only on successful settlement. | Denial consumes none; a customer override can authorize the same outstanding request. Gateway idempotency and retry reconciliation remain to be built. |
| Cross-customer spending or overspending | Available and locked balances are separated by customer/session; signed service scope, per-request maximum, remaining balance, and hard budget are enforced before evaluation. Conservation invariants cover randomized multi-session operation. | Concurrent offchain authorizations can compete for the same capped budget; the gateway must reserve and reconcile them. |
| Refund races outstanding charges | Early close retains the original refund deadline. Execution deadlines, receipt freshness, and the locked settlement window precede refund; refund always pays the fixed customer. | Provider timestamps are reported evidence, not an independent clock or delivery proof. Closing cannot independently prove when a provider actually executed work. |
| Malformed, unavailable, or expensive processor | Exact metadata/netlist checks, bounded calls, strict output ABI, fail-closed denial. | Upstream circuit factory is unsealed and unaudited. |
| Upstream upgrade | Beacon implementation and processor/implementation code hashes are pinned and checked each evaluation. | A malicious owner can temporarily upgrade, alter storage, and restore code. These checks cannot prove storage history untouched. |
| Reentrancy and unsafe token calls | ReentrancyGuard, SafeERC20, effects before payout, fixed DemoUSD, deposit/payout balance-delta checks, and an explicit provider allowlist. Failed payout reverts spending and consumed identifiers. | Arbitrary, rebasing, or fee-charging tokens are unsupported. The deployed engine uses the original DemoUSD only. |
| Credential exposure | User-authorized signer file stays outside the repository; signing happens locally; public journals contain only addresses/signatures/receipts. | Online production provider keys and relayer operation need their own key management. |
| Fabricated settlement status | Actual transaction inputs, receipts, balances, circuit bytes, and verdicts are recorded. Fork artifacts are labelled separately. | A mined receipt with one confirmation is not a claim of Ethereum L1 finality. |

The vault exposes no administrator withdrawal of customer balances. Refunds remain available after the window even if the TapeOut adapter becomes unavailable. A reverting denial has no persistent contract event; its reverted transaction and the verified simulation reason provide the proof record.
